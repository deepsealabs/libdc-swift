## [Unreleased]
### Added
- macOS: serial cable downloads. `IOKitCableDiscovery` lists USB-serial ports from the IORegistry (`IOSerialBSDClient`, with the VID, PID, serial number and product name read from the USB device's own entry, so an adapter with no serial never takes its hub's) and follows hot-plug through an `IONotificationPort`, without opening any port. Built-in ports and the Bluetooth listening port are left out; paired classic-Bluetooth ports are listed as `.classicBTSerial` (Beta; see the classic-Bluetooth entry). A known cable with no port is listed as `driverMissing`, once a cable that arrived after `start()` has gone `driverGrace` (3 s) without one, and `CableEndpoint.driverMissingMessage` says which driver to install and where; `driverMissingStoreMessage` says what to do with no download link or install step, for an App Store build. `CableDiscovering.updates()` streams `[CableEndpoint]` (`ready`, `driverMissing`, or `busy` while a session in this process has the port), and `StaticCableDiscovery` serves endpoints you set. Both map a `RegistrySnapshot`, so the mapping runs on fixtures
- macOS: `CableHints`, the cable or chip a VID:PID is: Suunto (0403:F680), Cressi (0403:87D0) and Oceanic/Pelagic (0403:F460, which needs FTDI's driver) offer only their own families; FTDI FT-X/FT232R (OSTC first), FT2232/FT4232 (OSTC and Suunto first), the Mares Icon HD's USB-CDC interface (FFFF:0005, Icon HD first), CP210x, PL2303 and CH34x offer every serial model. The Prolific cables with Epson's VID (04B8:0521 Mares/Cressi, 04B8:0522 Zeagle) and the CP2108 (10C4:EA71), which macOS has no driver for, are listed as `driverMissing` with a message that says so. Which cables macOS drives itself was read from macOS 26.4's driver personalities, and every FTDI hint carries FTDI's driver page as a fallback `driverURL`
- macOS: `DiveComputerSession.open(_:model:discovery:recorder:deviceStorage:lease:)` opens a serial endpoint through a `TapStream`, throwing `CableError`. The port is opened once, as libdivecomputer does; only when `dc_serial_open` fails does a second `open` read errno, to tell busy (EBUSY) from not permitted (EPERM, EACCES), which `dc_serial_open` reports alike. A model with no descriptor is refused as `unsupportedTransport` before the port is touched. Cancelling the task throws `cancelled` at once, even while `open(2)` is stuck, and a session the stuck open makes later is closed; opens don't queue behind each other. The session lease is taken only once the port is open, so an `open(2)` that never returns blocks only another open of the same port. A cancel that lands as the open finishes closes the session. With a started discovery, pulling the cable cancels the session and sets `wasUnplugged`. `close()` on an owned cable session runs the driver's quit with its sleeps (Cressi Goa needs 100 ms before its exit command), and `TapStream.beginClosing` caps each read at `closingReadLimitMilliseconds` (500 ms), so a computer that stopped answering can't hold the close for the driver's timeout. A cable session's close that reaches the main thread (`close()` there, the end of a download a close waited for, or the session's last release) runs on a background queue; the lease is held until the port is closed, and `close(completion:)` reports when it is. A cable session's `StoredDevice` is keyed by the cable's locator, so it describes the last computer reached through that cable. A cable session with no stored record stores the hardware's model under the family it opened, not one its name matches
- macOS: `open_serial_device` (LibDCBridge) resolves the descriptor, opens the port with `dc_serial_open`, hands it to a wrap callback (the tap), and opens the device with one attempt (`LIBDC_SERIAL_OPEN_ATTEMPTS`). It takes ownership of the context on every path
- macOS: `CableError` (`permissionDenied`, `busy`, `sessionInProgress`, `notFound`, `driverMissing`, `unplugged`, `noResponse(family)`, `cancelled`, `unsupportedTransport`, `portError`, `protocolError`), with `CableError(download:session:)` for a download that ended early (nil for `.parseRejected`, a parser hold, not a cable fault; it reads the family the session opened, so it is safe after `close()`) and an English `message`. `noResponse`'s message adds `DeviceCatalog.cableConnectInstructions(for:)`, what to do on each family's computer before a cable download
- Tests: discovery mapping on registry fixtures and over a fake hot-plug source, cable sessions over a pseudo-terminal through `dc_serial_open` (line settings, timeouts, cancel, unplug, refusals), and a classic OSTC download, from an emulator built from libdivecomputer's protocol code, recorded over a pty and replayed through `ScriptedStream` (`hw_ostc_mk2_synthetic.dcrec`, synthetic values with the serial scrubbed). `SerialHardwareTests`, run with `LIBDC_SERIAL_PORT` and `LIBDC_SERIAL_MODEL`, downloads a real computer twice and records a serial-scrubbed `.dcrec` into `Fixtures/Hardware`, which `SerialReplayTests` replays. Details in `Docs/MACOS_SERIAL_CABLES.md`
- macOS: USB HID downloads. `HIDStream` is a `DCUSBHIDStreamBackend` on a computer's own `IOHIDDevice`, behind the `HIDDeviceIO` seam (`IOKitHIDDevice` is the live device), opened through `DCCustomStream` as `DC_TRANSPORT_USBHID` so the EON Steel and Uwatec Smart drivers take their USB HID paths. Each operation answers as `usbhid.c`'s hidapi build does: a read is one report with its report-ID byte as delivered, cut to the requested size; a positive timeout that passes is `TIMEOUT` (hidapi's `SUCCESS` with 0 bytes becomes `PROTOCOL` in both drivers, which a download with a stored fingerprint would report as no new dives), and a 0 timeout with nothing waiting is `SUCCESS` with 0 bytes; a write with report ID 0 sends the bytes after it, any other report ID is sent as the report's first byte, and `actual` is the whole size either way; `poll` and `ioctl` are `UNSUPPORTED`; at most 1024 unread reports are kept, and a dropped report fails the next read with `IO`. The lifecycle follows `IOHIDDevice.h`: the callbacks, dispatch queue and cancel handler are set before `IOHIDDeviceActivate`, and the cancel handler closes the device, after an unplug too as hidapi does on macOS 10.10+, and only then releases it and the report buffer. A removal marks the session unplugged before it wakes a blocked read. No HID library is vendored and `HAVE_HIDAPI` stays undefined. Details in `Docs/MACOS_USB_HID.md`
- macOS: `IOKitCableDiscovery` lists USB HID dive computers (EON Steel, EON Core, D5, EON Steel Black, G2 / G2 TEK, G2 Console, G2 HUD, Aladin Square) before serial ports. They come from an `IOHIDManager` matching only vendor IDs 0x1493, 0x2e6c and 0xc251 (`HIDVendors.vendorIDs`), which is never opened, so listing never raises the Input Monitoring prompt. Other devices on those vendor IDs (Suunto watches, Keil debug probes) are left out, and so is a keyboard or mouse interface beside another interface of the same VID:PID; a computer's only interface is listed whatever usage page it declares. Discovery logs how many HID devices each vendor ID matched, listed and rejected. New: `CableEndpoint.usbHIDDevice(registryID:vendorID:productID:serialNumber:productName:)`, `CableEndpoint.registryID` and `RegistrySnapshot.hidDevices`
- macOS: `DiveComputerSession.open(_:model:discovery:recorder:deviceStorage:lease:)` opens USB HID endpoints too, through a `TapStream`, seizing the device as hidapi does. A model the VID:PID can't be is refused before the device is touched; 2e6c:3201 opens as a G2 or a G2 TEK, and DEVINFO names the computer. `kIOReturnExclusiveAccess` is `CableError.busy`, `kIOReturnNotPermitted` is `permissionDenied`, a device gone before the open is `notFound`, and `CableError.usbError(ioReturn:)` is any other open failure. The device's own removal callback ends a download and sets `wasUnplugged`, with or without a discovery. Cancelling ends a blocked read within 100 ms. The `busy`, `permissionDenied` and `notFound` messages name the dive computer as well as the cable, and `cableConnectInstructions(for:)` has EON Steel and Uwatec Smart entries
- Tests: `HIDStreamTests` (the lifecycle, against a fake `IOHIDDevice` that fails on anything `IOHIDDevice.h` forbids, and the hidapi semantics), `HIDCableSessionTests` (libdivecomputer's EON Steel and Uwatec Smart drivers against emulated computers, with synthetic values), `HIDDiscoveryTests`, and the `HIDHardwareTests` harness, which runs against a real computer with `LIBDC_USBHID_MODEL` set
- macOS (Beta): raw USB downloads for the Atomic Aquatics Cobalt and Cobalt 2 (0471:0888), libdivecomputer's only `DC_TRANSPORT_USB` family. `USBStream` (LibDCBridge, `USBBridge.m`) is a `dc_custom_open` stream on IOUSBLib (`IOCreatePlugInInterfaceForService`, `IOUSBDeviceInterface500`, `IOUSBInterfaceInterface500` on interface 0) that answers every operation as `usb.c`'s libusb build does: bulk reads on 0x82 and writes on 0x02, the `DC_IOCTL_USB_CONTROL_READ`/`_WRITE` ioctl built from `dc_usb_control_t` (a `wLength` past the buffer is `INVALIDARGS`), `set_timeout` 0 `UNSUPPORTED`, and a timed-out read returning `TIMEOUT` with the bytes that came before it, which `atomics_cobalt.c` relies on. Reads go one max-size packet at a time, because a timed-out `ReadPipeTO` reports no count; that costs about 1 ms a packet behind a USB 2 hub. A timed-out read clears nothing (libusb clears a pipe only on IOUSBFamily 245 or older); a real stall is cleared and is `IO`. An underrun that left the count unchanged is `IO`. A cancel is cooperative, as upstream's: one that lands mid-dive lets the dive finish, reading and dropping the rest, before `CANCELLED`, and one that lands while a request is on the wire still reads its reply, so the Cobalt is never left with part of a dive on its IN pipe; `TapStream` passes raw USB reads through after a cancel so the stream can do this. Only a transfer with no timeout, or one on a device the registry has seen go (`USBStream.abortCheck`), is aborted, within 50 ms. `HAVE_LIBUSB` stays undefined and no USB library is bundled. Details in `Docs/MACOS_USB.md`
- macOS: `IOKitCableDiscovery` lists raw USB computers (`transport == .usb`, `id` `usbdevice:<registry id>`) after USB HID computers, from `RegistrySnapshot.usbComputers`, and follows them through vendor ID 0x0471. New: `CableEndpoint.usbDevice(registryID:vendorID:productID:serialNumber:productName:)`, `USBComputers` and `USBInterfaceLayout` (`usb.c`'s `g_usb_config`), and the `USBDeviceIO` seam with `IOKitUSBDevice` as the live device
- macOS: `DiveComputerSession.open(_:model:discovery:recorder:deviceStorage:lease:)` opens raw USB endpoints too, through a `TapStream` (channel `"usb"`). `kIOReturnExclusiveAccess` is `CableError.busy`, `kIOReturnNotPermitted` is `permissionDenied`, a device gone before the open is `notFound`, any other open failure is `usbError(ioReturn:)`, and a transfer that finds the device gone marks the session unplugged, with or without a discovery
- macOS: Beta labels. `DeviceCatalog.betaFamilies`, `DCModel.isBeta(on:)` and `CableEndpoint.isBeta` say which models a transport reaches through a stream with no upstream-proven transport behind it: the Cobalt and Cobalt 2 on `.usb`. Hosts show them as Beta. No cable path, Beta or not, has run on a real computer yet
- Tests: `USBStreamTests` (`usb.c`'s operation table, the control setup's layout and `wLength` bounds, packet-by-packet reads, timeouts with partial counts, cancel and removal, against a fake interface with USB's bulk rules), `USBCableSessionTests` (libdivecomputer's Cobalt driver against an emulated Cobalt), `USBReplayTests` (hand-written Cobalt conversations through `ScriptedStream`), `USBDiscoveryTests`, and the `USBHardwareTests` harness, which runs against a real computer with `LIBDC_USB_MODEL` set
- macOS (Beta): classic-Bluetooth downloads for the Shearwater Predator, Petrel, Petrel 2, Nerd and Perdix, over the paired `/dev/cu.*` Serial Port Profile port, which serial discovery now lists as `.classicBTSerial`, offering the models the port's name starts with (a "Petrel" port offers the Petrel 2 first; an unmatched one offers all five with the Predator last; `DeviceCatalog.pairedBluetoothCandidates(portName:)`, `CableEndpoint.pairedBluetoothPort(path:baseName:)`). `DiveComputerSession.open` opens it through `open_serial_device` as a USB-serial endpoint, since it is `DC_TRANSPORT_SERIAL` too, but first waits up to 20 s for carrier, polling every 50 ms, because the port opens and takes writes before bluetoothd has connected the link and Shearwater's first request is never resent; it goes ahead if carrier never rises. On that port the tap raises any positive read timeout to 12 s (`TapStream(readTimeoutFloor:)`, `bluetoothReadTimeoutFloorMilliseconds`), Subsurface's Shearwater value. `CableSupport.transports` includes `.classicBTSerial` on macOS. `DeviceCatalog.betaFamilies` adds `.classicBTSerial: [.shearwaterPetrel, .shearwaterPredator]`, so every model it offers is Beta. `cableConnectInstructions(for:)` gives these two families Bluetooth-specific wording instead of "attach the cable", since they have none. Details in `Docs/MACOS_SERIAL_CABLES.md`
- macOS: `CableError.bluetoothNotConnected`, for a `.classicBTSerial` session that timed out or failed before the computer sent a byte (a computer not connected most likely reads this way; ENOTCONN on the port maps to it too, on paired ports only), and `CableError.bluetoothLinkLost`, for a link that answered (sent a byte, or delivered a dive) and then dropped; `CableError(download:session:)` gives the same answer after `close()`. The paired port stays after the link goes, so neither reads as an unplug. `TapStream.bytesRead` counts what the inner stream returned

## [1.21.0] - 2026-11-05
1.8.0 to 1.20.0 were tagged without sections of their own; everything they and 1.21.0 shipped is listed here.
### Added
- Suunto Nautic/Ocean: a dive whose download a dropped link (or a cancel) cut short carries on from the bytes already received on the next connection, instead of starting again from offset 0. The driver keeps the compressed `/Data` received so far in a buffer per watch (`suunto_nautic_device_set_resume` / `_get_resume`, fork only). The next download of that dive, by `dc_device_foreach` or by id, fetches the `/Summary` first, which gives the size of the whole `/Data`, then GETs the `/Data` again and reads only what is missing in pages from the first missing byte; a dive whose whole `/Data` arrived (a lost end marker, a drop at the stream's close or at the `/Summary`) needs only the `/Summary`. If the watch won't serve the pages, the dive is streamed from the start in the same attempt. `SuuntoNauticResume` holds the buffers and `openBLEDevice` attaches it to every Nautic/Ocean device, so the Explorer, Auto download and `retrieveDiveLogs` all resume. Up to 4 dives are kept per watch, in memory only; a success, any failure other than the link's, or a resume that times out without getting further forgets the dive, and it is still checked against its listed size. Auto download logs "carrying on from byte N" and `NauticSyncLink.resumableBytes(of:)` reports it. From trustthegoose's build 26 traces: after every real drop the watch answered the new GET of the same `/Data` with 200 and the same handle. On the Oct 23 Ocean traces, pages of 451 bytes ran at about 6.6 KB/s against about 8 to 9 KB/s for the stream, so a resume is slower than starting over only when very little was kept (#29, #101)
- `set_libdc_log_sink`/`attach_libdc_log`: libdivecomputer's ERROR/WARN/INFO lines reach a host log, not only the console, so a bare `DC_STATUS_DATAFORMAT` comes with its reason (e.g. "Invalid logbook end pointer"); the parser context logs too
- DC Tester: Share log carries libdivecomputer's ERROR/WARN/INFO lines (e.g. the Nautic's "reading the rest in pages"); a failed download names its reason and `DC_STATUS_…` instead of an empty "Download failed: ", and "Downloaded N dive(s)" counts this run, not the session
- `RawDiveEvent` on `DiveProfilePoint.rawEvents`: every `DC_SAMPLE_EVENT` with its payload (`rawType`/`type`, `value`, `flags`, `phase` begin/end, `timeOffset`), including types `DiveEvent` has no case for
- `DecoKind` on `DiveProfilePoint.decoKind`: NDL, safety stop, deco stop or deep stop, from `DC_SAMPLE_DECO`
- `NauticAutoSync`: hands-off Suunto Nautic/Ocean download. Waits for the watch, downloads only dives whose logbook id isn't synced yet, listens for the watch's `/Logbook/UnsynchronisedLogs` and `/Sync/BusyState` pushes while connected, and reconnects under a `ReconnectPolicy` that mirrors the Suunto app (4 s retry, 20/96 attempt caps, 120 min cool-down, loop detection), resuming with the dives still missing (#45)

- DC Tester: a by-id download whose bytes belong to another dive says so in the status and the Last Response header, which always name the id requested
- `DiveDataViewModel.lastDownloadInterruption`: set when a download delivered some dives and then failed, so the app can say "some dives couldn't be downloaded, reconnect and sync again"
- `NauticAutoSync.Configuration.connectTimeout` (25 s): a connect attempt that hasn't finished is cancelled (`NauticSyncConnector.cancelConnect()`), the `watchUnreachable` event fires with a "press a button on the watch" hint, and the sync falls back to scanning; DC Tester shows the hint in its status (#29)
- DC Tester: "Download all (ignore fingerprint)" switch next to Download Dives

- Suunto Nautic/Ocean: the water type set on the watch (fresh, EN13319, salt) from the `/Summary`, as `DiveData.salinity` (#29)
- `suunto_nautic_device_handshake_acknowledged` / `SuuntoNauticExplorer.handshakeAcknowledged(device:)` and `DiveDataViewModel.lastHandshakeAcknowledged`: whether the watch answered the open's handshake. The open still succeeds without it, so a sleeping watch's first request times out; apps can say "press a button on the watch" (#29)
- DC Tester: the Explorer says when the watch hasn't answered since connecting, and keeps an exportable log of its connects, commands and results (Share / Copy / Clear) (#29)
- `SuuntoNauticExplorer.fetchPaged(device:path:)` (`suunto_nautic_device_fetch_paged`): every page of any paged resource, so `/Logbook/byId/<id>/Descriptors` comes through whole; DC Tester's Explorer uses it for Descriptors as well as `/Summary` (#72)

The completion runs on main once the device is released and says whether a close was waiting

- Internal: `DeviceStorage` and `DeviceFingerprintStorage` take an injected `UserDefaults` suite (`init(userDefaults:)`, defaulting to `.standard`); `DeviceStorage` also takes an injected fingerprint store so `removeDevice`'s cleanup can be isolated (`init(userDefaults:fingerprints:)`)

- `open_device_on_iostream` (LibDCBridge): opens a device on an iostream the caller already opened (a serial port, a custom stream) with a chosen number of `dc_device_open` attempts and wait between them. It takes ownership of the context and iostream on every path: on failure both are released and the `device_data_t` is zeroed. `open_ble_device` now opens through the same code with its existing 5 attempts 3 s apart (`LIBDC_BLE_OPEN_ATTEMPTS`, `LIBDC_BLE_OPEN_RETRY_MS`), still resolving the descriptor before it connects
- `find_descriptor_by_name_transport` (LibDCBridge): descriptor lookup by name for one transport. `DC_TRANSPORT_BLE` is exactly `find_descriptor_by_name`; serial, USB and USB HID match "Vendor Product" (first in table order), and classic Bluetooth and IrDA fall back to libdivecomputer's name filter
- `libdc_set_cancel` (LibDCBridge): installs or clears the cancel callback on an open `device_data_t`
- `libdc_cable_transports()` (LibDCBridge): the cable transports this platform can reach, `DC_TRANSPORT_SERIAL | DC_TRANSPORT_USBHID` on macOS and none on iOS (checked at compile time), because `dc_context_get_transports` always reports serial
- DC Tester Mac: a sandboxed macOS probe for serial (including libdc line control), USB-HID (with an identify round trip), IOUSBLib, BLE and Garmin volume access, plus the built-in serial driver table, which produces the cable go/no-go matrix in `Docs/MAC_SANDBOX_PROBE.md`
- `DiveComputerSession`: an open dive computer on any transport. `open(iostream:context:family:model:...)` opens a device on an iostream the caller opened (owning both, as `open_device_on_iostream` does) and closes it in `close()`; `adopt`/`adoptBLE` wrap a device someone else opened. `cancel()` is sticky, and on non-BLE sessions it also fails the next transfer through `libdc_set_cancel`. `close()` during a download cancels it and closes when it ends. An adopted BLE link shares its `CoreBluetoothManager`'s close deferral (`adoptBLE`, or `adopt(...bluetoothManager:)`), so the manager's `close` during a session download cancels the download's I/O and waits for it, and the session lets go of the device before it is freed; an owned session holds its own close the same way
- `DiveComputerSessionLease`: one open `DiveComputerSession` at a time, BLE or cable; `open` and `adopt` throw `DiveComputerSessionError.busy` while another session holds it. It serializes sessions only: auto download's `NauticLinkLease` and legacy `openBLEDevice` connections don't take it. While it is held, `openBLEDevice` doesn't close the open device first, so a device an adopted session wraps isn't closed under it
- `DiveLogRetriever.retrieveDiveLogs(session:viewModel:syncClock:useFingerprint:onProgress:completion:)`: the download over a session, with a commit-acknowledge fingerprint contract. It completes with a `DiveDownloadResult` (`completed`, `noNewDives`, `cancelled`, `emptyRead`, `parseRejected(count:status:)`, `interrupted`, `failed`, plus dive and parse-failure counts and `unreadableDives`) and saves no fingerprint itself: `fingerprintCommit` is offered only when the walk finished with no dive held, and the stored fingerprint moves only when the host calls `acknowledge()` on it. Rejected dives follow the `CBPeripheral` download's rule: a dive the parser rejects for the first time holds the fingerprint and the download ends `.parseRejected` with the parser's status, and the same dive rejected on a later download is skipped as unreadable (listed in `unreadableDives` and `DiveDataViewModel.lastUnreadableDives`) so the commit moves past it. A cancel or a close mid-download saves nothing and reports `.cancelled` with `DC_STATUS_CANCELLED`, whatever the driver returned, and sets `lastDownloadStatus` and `lastDownloadInterruption` as the `CBPeripheral` download does (`"CANCELLED"`). A dive the session has no parser configuration for holds the fingerprint on every download, so the commit never moves past it. The view model the C fingerprint lookup reads is retained until the session closes. Dives from a driver that reports no fingerprint (Suunto Solution) are still downloaded and parsed, but no commit is offered, so every download fetches all of them again
- `FingerprintCommit.acknowledge()` saves on the main thread (at once when called there, else on the main queue's next turn). `DiveDownloadResult` and `FingerprintCommit` (with a `save` closure) have public initializers so hosts can build results in their own tests
- Session downloads date Reefnet Sensus, Sensus Pro and Sensus Ultra and Uwatec Memomouse dives from the `DC_EVENT_CLOCK` devtime/systime pair (`dc_parser_set_clock`); without it those parsers count device ticks from 1970
- Session downloads parse with the descriptor the session opened when the hardware reports a model no descriptor knows, and never store such a model (or an unreported model 0) in `DeviceStorage`, since the next open looks the stored model up
- `libdc_close_device_data` (LibDCBridge): releases everything a successful open left in a `device_data_t` and clears its fingerprint lookup (`fingerprint_context`, `lookup_fingerprint`)
- macOS: `DCCustomStream.open(backend:transport:context:)` opens a `dc_custom_open` iostream on a Swift `DCIOStreamBackend`, a protocol with all 15 iostream operations required. It always installs all 15 callbacks, because `custom.c` answers `DC_STATUS_SUCCESS` for a missing one without calling anything (a skipped DTR, RTS or sleep), and keeps the backend alive until `dc_iostream_close`. `DCUSBHIDStreamBackend` and `DCUSBStreamBackend` answer the operations `usbhid.c` and `usb.c` leave out exactly as upstream does (`SUCCESS`, lines and available 0, no sleep, `UNSUPPORTED` poll, and `UNSUPPORTED` ioctl on HID), so a backend implements only the transfers
- macOS: `TapStream` wraps an opened iostream (a `dc_serial_open` port, say) and forwards every operation. A blocked read, poll or sleep gives up with `DC_STATUS_CANCELLED` within 100 ms of its cancel check turning true (`isCancelled:` / `setCancellation(_:)`); reads poll in 50 ms slices and keep the inner stream's -1/0/N ms timeout rules and partial counts, and packet streams (BLE, USB HID) still get one report per read. Writes can't be interrupted. While `Logger.shouldShowRawData` is on, packets go to `Logger.onPacket` with a channel (`"serial"`, `"usbhid"`, or one you pass), and an optional `DCStreamRecorder` records every operation
- macOS: `DCRecording`, a recorded iostream conversation saved as a `.dcrec` file (JSON, one exchange per line). It holds no port path, adapter serial or wall-clock time, and `DCRecordScrubber` (`.replacing(_:)`, `then(_:)`, or your own) rewrites the device's serial, dates or positions in `DCStreamRecorder.recording()`, seeing each direction as one stream so a pattern split across reads is still caught
- macOS: `ScriptedStream` replays a `DCRecording` or hand-written exchanges to a driver, strictly: an unexpected configure, DTR, RTS, write or read size, or anything past the end, fails with `DC_STATUS_IO` and is kept in `deviation`. Replays don't wait, so a recorded download, unplug or timeout reruns in milliseconds
- `PacketEvent.channel`: the link a packet crossed, `PacketEvent.bleChannel` (`"ble"`) for every BLE packet, or a cable stream's channel. `characteristicUUID` is unchanged, and empty on cable channels
- `DCTransport` (`ble`, `serial`, `usbHID`, `usb`, `classicBTSerial`), with stable raw values for storage and `dcValue`, the iostream transport a download opens with. A paired classic-Bluetooth port is a serial port. `CableSupport.transports` is `[.serial, .usbHID]` on macOS and empty on iOS
- `DeviceCatalog`: every libdivecomputer descriptor as a `DCModel` (vendor, product, family, model, transports, canonical name), read from the descriptor table at runtime. `models(for:)` gives 283 serial, 10 USB HID, 2 USB and 117 BLE models with the bundled libdivecomputer. Shearwater's 5 `SERIAL` descriptors are its paired Bluetooth SPP port, so they are `.classicBTSerial` and are never offered as a cable. `candidates(vid:pid:transport:)` narrows libdivecomputer's family-wide USB filter with an exact VID:PID table (EON Steel, EON Core, D5, EON Steel Black, G2 / G2 TEK, G2 Console, G2 HUD, Aladin Square)
- `DeviceCatalog.canonicalName(family:model:)`: the first `supportedModels` entry with that family and model, else the first descriptor in table order. Family and model don't name one product (G2 and G2 Console are both Uwatec Smart 0x32), and stored devices and existing fingerprints already carry `supportedModels` names
- `DiveComputerIdentity`: family, model, canonical name, serial, firmware and transport, read from DEVINFO. A serial of 0 is unknown. `deviceKey` is `"sn:<serial>"`, else `"md:<canonical name>"` lowercased, the same keys hosts dedupe dives on, on every transport. `storageKey(standIn:)` is the fingerprint key: family plus serial, else, with no serial, the model plus a stand-in for the unit (a cable adapter's USB serial, or the BLE peripheral's identifier); with neither there is no key, so nothing is stored and every download fetches every dive. `init?(device:transport:)` reads one from an open `device_data_t`
- `DiveComputerLocator` (`ble`, `serial`, `usbHID`, `usb`, `classicBTSerial`): where a computer was reached, kept as provenance (`locatorKey`), never as identity. `unitStandIn` is the stand-in for a computer that reports no serial
- `DiveComputerSession.identity` and `locator`, `DiveDownloadResult.identity` and `FingerprintCommit.identity`. `open` and `adopt` take a `locator`, and `adoptBLE` passes the peripheral's
- `StoredDevice.transport` (nil on older records, which read as BLE through `effectiveTransport`) and `locator`, the `DiveComputerLocator` it was last reached through (`locatorKey` is its string form), which `storeDevice` keeps unless it is given new ones. A locator this version can't read decodes as nil and keeps the record. `DeviceStorage.storedDevice(family:serial:)` finds the most recently connected record of one computer on any transport
- Fingerprints keyed by identity: `DeviceFingerprint.key`, and `DeviceFingerprintStorage.getFingerprint(for:standIn:)`, `saveFingerprint(_:for:standIn:)`, `clearFingerprint(for:standIn:)` and `seedFingerprint(identity:data:standIn:)`, also on `DiveDataViewModel`. Lookups fall back to a record saved by 1.18 with the same family and serial, so an unmigrated store never forces a full download. Saves keep the device type and serial a 1.18 reader looks up. `seedFingerprint` stores a fingerprint from a dive the host already has, so the first download on a new host stops there, and never replaces a stored one
- `DeviceFingerprintStorage.migrateLegacyKeys(storedDevices:)` / `DeviceStorage.migrateFingerprintKeys()`: give 1.18 records their identity key in place, leaving their device type, serial, fingerprint and timestamp unchanged. A record with serial 0 is keyed only when exactly one serial-0 BLE device of its family is stored. Idempotent. Details in `Docs/DEVICE_IDENTITY.md`
- Rejected dives keyed by identity: a session download remembers the dives the parser rejected under the computer's `storageKey(standIn:)` and reads and writes the 1.19 `"<device type>|<serial>"` entry of the same family and serial too, and the `CBPeripheral` download writes both keys. A dive rejected over BLE is skipped as unreadable the next time a cable download rejects it, and the other way round. `migrateLegacyKeys` copies 1.19 entries to their identity key and keeps them, and clearing a computer's fingerprints clears its rejected dives under every key

### Changed
- `DeviceConfiguration.DeviceFamily` has a case for every libdivecomputer family (47; it had the 17 BLE ones). The existing cases and their raw values are unchanged, but an exhaustive `switch` over it without `default` no longer compiles, `allCases` grows, and `DeviceFamily(dcFamily:)` and decoding accept the new families
- Session downloads look up and commit fingerprints by `DiveComputerIdentity`: the C lookup's context is the session, and it keys on DEVINFO instead of the descriptor's name. A commit's `deviceType` is the canonical name, so a G2 Console's is "Scubapro G2". A computer that reports serial 0 gets a commit only when its locator has a stand-in, and serial 0 is never stored as a stored device's serial. A stored device a session download creates or updates gets the session's transport and locator. The `CBPeripheral` download still keys by `(deviceType, serial)`, unchanged
- Session downloads give Zeagle N2iTiON3 (and its rebadges) and Citizen Hyper Aqualand, whose drivers never send DEVINFO, the opened descriptor's identity with no serial, so `DiveDownloadResult.identity` and `deviceKey` exist. With a stand-in, the stored fingerprint is set on the device before the walk and the commit is keyed by the stand-in; without one, every download is full
- `DeviceStorage.removeDevice(uuid:)` also clears the device's identity-keyed fingerprint, including a serial-0 cable computer's, keyed by its locator's stand-in
- `StoredDevice.swift` no longer imports CoreBluetooth
- The `CBPeripheral` `retrieveDiveLogs` overload keeps its contract unchanged (it saves the fingerprint itself, with the same rejected-dive, host-stop and close handling) and now runs on the same download core as session downloads
- `device_data_t.have_clock`/`clock` are filled from `DC_EVENT_CLOCK`, which was subscribed but dropped
- `NauticLinkLease` is built on `DiveComputerSessionLease`; its behaviour and its own shared instance are unchanged
- Suunto Nautic/Ocean, following the third round of Jef Driesen's review of libdivecomputer#73: the driver no longer retries a stream or a dive, which replaces the stream and download retries of the second round below. A refused `/Data` stream, a stream that stops before its end marker or has a chunk at an earlier offset, an unanswered GET or SUBSCRIBE of `/Data`, and a dive that doesn't add up to its listed size fail the dive on the first attempt (`DC_STATUS_PROTOCOL` or `DC_STATUS_TIMEOUT`), and `dc_device_foreach` stops at that dive with only the newer dives delivered. Apps must retry a failed dive themselves, on the same link or after a reconnect. Auto download already does (`retriesPerDive`); a caller of `retrieveDiveLogs` or `SuuntoNauticExplorer.download` should offer to sync again
- Suunto Nautic/Ocean: a lost `/Data` chunk no longer fails the stream. The rest of the dive is read in pages on the same handle from the first missing byte, as the Suunto app does, and is still checked against the listed size. This follows a PacketLogger capture of the Suunto app on an Ocean (#29) and hasn't run against a real watch yet
- Suunto Nautic/Ocean: an entry listed with size 0 is skipped with a warning, without downloading it. A by-id download of a dive that isn't listed is still downloaded without the size check
- Suunto Nautic/Ocean: a `/Logbook/Entries` page must be exactly its header and records, or the listing fails with `DC_STATUS_PROTOCOL`
- Suunto Nautic/Ocean: the driver delivers a dive whose profile doesn't start with `SBEM0103` as downloaded, instead of skipping it while `dc_device_foreach` reports success, and the parser rejects it with `DC_STATUS_DATAFORMAT`. An app that parses the dives itself sees the rejection and can keep the dive pending (auto download's `onDive` throws); `retrieveDiveLogs` keeps the stored fingerprint and reports the download as failed (see Fixed)
- Suunto Nautic/Ocean, following the second round of Jef Driesen's review of libdivecomputer#73: a dive is never delivered possibly truncated. A `/Data` stream that stops before its end marker or has a chunk at an unexpected offset is issued again, and if it still fails, or the dive doesn't add up to the size the watch lists, the download fails. A dive whose `/Summary` can't be fetched fails too, and RELEASE/UNSUBSCRIBE errors are reported
- `suunto_nautic_device_download` (`SuuntoNauticExplorer.download`) no longer returns a dive that doesn't match its listed size as `DC_STATUS_DATAFORMAT` / `incompleteDownload` with what arrived; it fails like any other download. Auto download retries such a dive on the same link and reports it as failed once its retries run out, instead of keeping the short copy
- Suunto Nautic/Ocean: a dive stream that stops before its end marker, and an unanswered GET or SUBSCRIBE of a dive's `/Data`, are issued again before the download fails with `DC_STATUS_TIMEOUT`, so a watch that stops answering takes up to about 20 s longer to report it. A by-id download whose listing times out returns that error straight away
- Auto download: a dive whose download keeps timing out while the link otherwise works is reported as failed once its retries are used up, and the next session moves on to the newer dives instead of reconnecting for it indefinitely
- Suunto Nautic/Ocean: the driver no longer releases a handle slot it didn't bind (another app on the link may hold it); it uses whichever slot the GET returns
- Suunto Nautic/Ocean: every packet from the watch goes through one receive path that checks its start byte, length and CRC and matches it to its request by sequence number, following Jef Driesen's review of libdivecomputer#73. Replies to the Suunto app's requests on the same link are skipped instead of being read as ours, which made a sync with the Suunto app still connected time out. The `/Data` stream ends on the watch's end marker with each chunk's offset checked, and `/Logbook/Entries` is parsed by its records
- GenericParser closes a profile point when the next `DC_SAMPLE_TIME` arrives (or parsing ends), so depth, events and deco land on the sample they were reported in instead of the following timestamp
- Repeated `DC_SAMPLE_TIME` callbacks with the same time continue one sample instead of adding duplicate points
- Events no longer append an extra profile point; they attach to their sample
- Deco fields are only set on samples where the computer reported `DC_SAMPLE_DECO`; safety and deep stops now fill `decoStop`/`decoTime`
- `SAMPLE_EVENT_SAFETYSTOP_VOLUNTARY` and `SAMPLE_EVENT_GASCHANGE2` map to their `DiveEvent` cases
- macOS: libdivecomputer builds with `HAVE_IOKIT_SERIAL_IOSS_H` and `HAVE_CLOCK_GETTIME`. Serial rates with no `Bxxx` constant (Sporasub SP2 at 460800, Cochran EMC at 850000) are set with `IOSSIOSPEED` instead of failing with `DC_STATUS_UNSUPPORTED`, `DC_IOCTL_SERIAL_SET_LATENCY` sets the receive latency with `IOSSDATALAT`, and serial timeouts use the monotonic clock. iOS builds are unchanged. Details in `Docs/MACOS_BUILD_DEFINES.md`

### Fixed
- `retrieveDiveLogs` appends each dive to `viewModel.dives` in that dive's own main-queue turn, so every dive is there when `completion` runs. The last dive used to land a turn after `completion` (and after `.completed`), so a host reading `dives` in `completion` missed the oldest new dive. A session download also numbers the dives, oldest first, before `completion`
- `DiveDataViewModel.updateProgress(count:)` no longer moves a finished download, or a `.cancelled` or `.failed` a host set, back to `.inProgress`. After a fast walk, a dive count could land after `.completed` or `.noNewDives` and leave the download looking unfinished
- A download's own progress reset lands in one main-queue turn, ahead of anything that download reports. It took two, so it usually cleared `lastHandshakeAcknowledged` just after the download set it, and a host could still see the previous download's end state when `completion` ran
- `DeviceFingerprintStorage` serializes its changes, so two at once (a launch-time `migrateLegacyKeys` and a commit, say) can no longer write back a list missing the other's
- Suunto Nautic/Ocean: a dive's start comes from `dc_datetime_mktime` rather than reading the parser's fields as UTC, so it stays the same instant when the parser reports the wall clock and offset the dive logged (deepsealabs/libdivecomputer#19)
- After a link drop the open device no longer talks into the dead link: `CoreBluetoothManager` forgets its characteristics and queued packets, and link I/O answers `DC_STATUS_NODEVICE` at once (`isLinkLost`, `ble_link_status`) until the next connect; `hasLostLink` tells the host to close the device. DC Tester closes it and says "Link lost. Tap Connect to reconnect." (#29)
- A connect right after closing a watch iOS holds the link to no longer loses its session to the close's delayed cancel (the same `CBPeripheral`): the cancel is skipped once a connect has started, and a link that already dropped is cancelled at once. Connect takes the link iOS re-established by itself (`retrieveConnectedPeripherals`), so the Hello is answered on our own session (#29)
- `open_ble_device` stops retrying `dc_device_open` once the link has dropped or a close waits (`DC_STATUS_NODEVICE`, `DC_STATUS_CANCELLED`). Each retry failed at once on the dead link, 3 s apart, which made up 12 of the 18 s before "Couldn't connect" in trustthegoose's build 24 run E (#101)
- DC Tester: a failed Explorer download no longer says to force-quit DC Tester and turn Bluetooth off and on; it says to reconnect from the device list, and how many bytes are kept to carry on from (#101)
- DC Tester: a finished download was written to the explorer log twice
- `DiveLogRetriever.retrieveDiveLogs` no longer stores a newer dive's fingerprint past a dive the parser rejects. The rejected dive was logged and skipped while `dc_device_foreach` still reported success, so the newest dive's fingerprint was saved and the rejected dive, if it wasn't the newest, was never downloaded again. The other dives are still delivered, the stored fingerprint is kept so the next sync downloads the rejected dive again, and the download completes with `completion(false)` and the parser's status (`DATAFORMAT` for a Suunto Nautic/Ocean profile without `SBEM0103`) in `lastDownloadStatus` and, when other dives arrived, in `lastDownloadInterruption`, whose new `divesRejected` counts the rejected dives. A driver error in the same download is reported instead. That next sync downloads again every dive since the stored fingerprint (the whole history on a first sync), not only the rejected one
- `retrieveDiveLogs` keeps the fingerprint for a rejected dive once. The parser gives the same bytes the same answer, so a dive the parser rejected on an earlier download and rejects again is skipped as unreadable: it no longer fails the download or holds the fingerprint, which moves past it (to the rejected dive's own fingerprint when it is the newest), and `lastUnreadableDives` lists it. Without this, a dive that can never be read failed every later sync and had each one download again every dive since the stored fingerprint. Rejections are remembered per device and serial until the dive parses, and are cleared with the device's fingerprint; a download with `useFingerprint: false` still downloads an unreadable dive and skips it straight away. A dive the driver gives no fingerprint can't be recognised again and always holds
- DC Tester: the Explorer's list, request, raw capture and by-id download calls run inside `withDeviceHeld`. Turning Auto download on, or going back and connecting another watch, while one of them was running closed and freed the device under it, the same `EXC_BAD_ACCESS` in `dc_iostream_read` the retriever had. The Explorer's Auto download switch is also disabled while it is busy, since that handoff starts the session on a timer instead of waiting for a held-back close
- Suunto Nautic/Ocean: a read that starts inside a frame, e.g. on a reconnect while the watch is still sending an interrupted stream, no longer stays out of phase until it times out. The HDLC layer discards empty frames and picks up at the next one
- Suunto Nautic/Ocean: the serial is the low 32 bits of the watch's 12-digit serial on every platform. Where `unsigned long` is 32 bits (Windows, 32-bit targets) every watch reported 0xFFFFFFFF and shared one fingerprint key; on 64-bit Apple platforms the value is unchanged
- Suunto Nautic/Ocean: a value the Suunto app's own subscriptions push during a dive stream on the same link is skipped instead of failing the stream with "Unexpected chunk size" (deepsealabs/libdivecomputer#15, @trustthegoose)
- `close(clearDevicePtr: true)` no longer frees a device `DiveLogRetriever.retrieveDiveLogs` is still downloading from. It used to close and deallocate the device while `dc_device_foreach` was still running on it, so the download's next read used freed memory and crashed (`EXC_BAD_ACCESS` in `dc_iostream_read`, seen on Suunto Nautic/Ocean right after the driver logged "Retrying the stream"). The close now cancels the download (BLE reads, writes and sleeps answer `DC_STATUS_CANCELLED`, and the device's cancel check is set) and runs, once, when `dc_device_foreach` has returned and before the retrieval's completion. That completion reports failure with the usual interrupted/incomplete status, and the fingerprint is not advanced. `openBLEDevice` waits for a close held back this way before opening another device (capped like its wait for the disconnect)
- `DeviceConfiguration.fetchDeviceInfo` is held back the same way: a close during its `dc_device_foreach` cancels it and runs once it has returned, and the completion reports `false`
- A close that cancels a download also wakes a BLE write waiting for a with-response confirmation or for the peripheral to accept a no-response write, and no further chunks of a split write go out, so the held-back close isn't kept waiting for the write timeout. A close still held back after 10 s is logged
- A download the app stops by clearing `isRetrievingLogs` no longer counts as complete. Drivers generally report a callback stop as success (the Suunto Nautic driver does), so the retrieval used to save the newest delivered dive as the fingerprint, and the next sync stopped there and never fetched the older dives the stop had left on the device. It now reports `completion(false)` with `progress` `.cancelled` and `lastDownloadStatus` `"CANCELLED"`, and keeps the fingerprint
- Aqualung i470TC is in `supportedModels`, so it can be picked for a sync
- Oceanic/Aqualung/Sherwood BLE names resolve against libdivecomputer's descriptor table instead of `supportedModels`. An i470TC ("GC004024") used to resolve to the Oceanic Pro Plus X, and BLE models missing from the catalog didn't resolve at all
- `DiveLogRetriever.retrieveDiveLogs` sets `CoreBluetoothManager.isRetrievingLogs` when it starts and clears it before calling `completion`, so callers no longer have to. A caller that didn't set it (DC Tester's Explorer "Download dives (all)") had its download cancelled on the first dive and got 0 dives. A cancel issued right after the call still wins (#79)
- `openBLEDevice` closes a device that's already open and waits for its link to drop before opening another, unless an auto download session holds the link. Opening a second watch on top of the first used to run the handshake on the first watch's link, so the open succeeded and the next request timed out (-7) until the old link dropped about 80 s later. `connect(toDevice:)` also clears the previous link's ready flag and characteristics before connecting (#75)
- DC Tester: the Explorer opens only after the new watch's open succeeds (it used to open straight away on the previous watch's device), names the selected watch on its connect line and on every command and result, and logs connect failures (#75)
- Suunto Nautic/Ocean: a second dive downloaded on the same link (by id, or the 2nd+ dive of a `dc_device_foreach`) can no longer stream the first dive's profile. The `/Data` stream is subscribed on the handle its GET returned, not a fixed one, and per-id handles are released after use (#29)
- Suunto Nautic/Ocean: `dc_device_foreach` no longer skips a dive whose download fails (a dropped link, an empty read of a listed dive) and reports success. It stops at that dive with the error, having delivered only the newer dives, so the stored fingerprint can't move past dives that were never fetched. Entries listed with no data are still skipped
- `retrieveDiveLogs` never reads a Suunto Nautic/Ocean `PROTOCOL` failure as "no new dives"
- Suunto Nautic/Ocean: dives over ~1.14 MB compressed are no longer cut short at 4096 stream frames, losing the ascent and safety stop (#60)
- Suunto Nautic/Ocean: each dive stream is closed with `STREAM_STOP`, and a GET's reply must echo its message id, so a leftover stream chunk can't make the `/Summary` fetch 404 (#59)
- Suunto Nautic/Ocean: `/Summary` pages drop their 11-byte header and CRC, so no bytes are lost at page boundaries (#57)
- Suunto Nautic/Ocean: every `/Logbook/Entries` page is listed (`StartAfterId`), so the newest dives on page 2+ are downloaded (#61)
- Suunto Nautic/Ocean: downloads are checked against the size the watch lists; `SuuntoNauticExplorer.download` throws `incompleteDownload` on a mismatch (#58)
- Dive time comes from the computer's `DC_FIELD_DIVETIME` instead of the last sample time, which counted post-dive surface logging (a Suunto Ocean dive timed at 1922 s by the watch came out as 37 min); falls back to the sample span when the field is missing or runs more than 60 s past the samples
- Average depth comes from `DC_FIELD_AVGDEPTH` when plausible, else the sampled mean clipped to the dive time
- Suunto Nautic/Ocean: the sync trigger subscription comes back after an automatic reconnect that followed a drop mid-download. Message ids now carry on from the previous connection instead of restarting at 1 (the watch can keep a dropped link's session and leave a repeated request unanswered); an unanswered subscription is retried 3 times 2 s apart and again later instead of being given up for the session; unsubscribing releases a per-id handle, and a 00 slot left bound by a dropped link is released when a GET lands on the 10 slot (#29)
- Suunto Nautic/Ocean: dive time is truncated like the Suunto app's (4680.5 s is 78:00, not 78:01), and dive time and max depth come from the watch's own values in the `/Summary` when they agree with the profile; max depth was the deepest logged sample, 0.2-0.3 m shallower than the app (#29)
- `retrieveDiveLogs(useFingerprint: false)` clears a fingerprint an earlier download on the same connection set
- Suunto Nautic/Ocean: on a reconnect a few seconds after a drop, opening the device waits for the watch's handshake reply, skipping the tail of the interrupted stream, before sending anything. The first request used to go out while the watch was still flushing that stream, and the Ocean left it unanswered about two times in three (#29, #45)
- Suunto Nautic/Ocean: helium is read from the gas record as an int16 at +3; it was read from O2's high byte, so every gas had 0 % helium and trimix decoded as nitrox (#29)
- Suunto Nautic/Ocean: average depth and the water temperature range are the watch's own, as the Suunto app shows them, when the `/Summary` agrees with the profile (#29)
- Suunto Nautic/Ocean auto download: switching from one watch to another no longer crashes. Every connector opens through the one shared `CoreBluetoothManager`, and the new watch's session could open its device while the old session was still unsubscribing and closing it. Sessions now take turns (`NauticLinkLease`), a stopped session cancels its in-flight download between stream frames instead of finishing it, and a closing link never closes another session's device (#29, #45)
- Suunto Nautic/Ocean auto download: turning it off and straight back on (same watch or another) no longer crashes. DC Tester's switch closed the shared device as a leftover manual session while the stopped session was still unsubscribing on it; it now leaves a device whose session holds the lease alone. A closing link also keeps the lease until its watch has actually disconnected, so a new session can't open into the old link's delayed cancel, and a late disconnect from one watch no longer resets the manager's state for another (#29)
- Suunto Nautic/Ocean: the water temperature range comes from the `/Summary` Windows records, which every watch writes in schema order, instead of the dive record's pair that Ocean firmware writes reversed; the dive record is the fallback (#29)
- Suunto Nautic/Ocean: a dive's Descriptors schema is no longer truncated at 64 pages
- Suunto Nautic/Ocean: when the Ocean stores the water temperature pair reversed, it is ordered instead of falling back to the sampled range
- Suunto Nautic/Ocean: tank end pressure is the watch's own at the end of the dive. It was the last reading, which after a dive with the valve shut and the regulator purged on the surface came out at 0.9 bar instead of 121.5 (#52)
- DC Tester: Download Dives says "No new dives since the last download" instead of "Downloaded 0 dive(s)" when the fingerprint stops it
- DC Tester: a failed download suggests reconnecting first and only calls a dive gone when `/Logbook/Entries` no longer lists it; Capture raw on a `/Summary` path fetches every page (#56)
- `DeviceStorage` decodes stored devices one at a time, so a record this version can't read (a family or transport from a newer version, say) is dropped on its own instead of emptying the whole list
- `DeviceStorage.reconcileUUID(name:newUUID:)` moves BLE records only, so a BLE scan can no longer re-key a cable record of the same name to a peripheral UUID
- `find_descriptor_by_name` returns `DC_STATUS_INVALIDARGS` for a NULL name or output pointer instead of crashing
